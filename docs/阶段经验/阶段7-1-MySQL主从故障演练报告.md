# 阶段7-1：MySQL 主从故障演练报告（2026-08-05）

> 验收项：MySQL 主从故障 **10 分钟内恢复** ✅（实测 ~1 秒）
> 环境：WSL2。主库 = 系统 MariaDB 10.11.14（3306），从库 = 手动实例（3307，普通用户 pc）。

---

## 一、演练目标

模拟主库宕机，验证：① 从库数据追平不丢 ② 从库转正可写 ③ 应用恢复时间 ④ 旧主库重接。

## 二、演练过程（全真实执行）

### 1. 主从复制搭建
- 主库开 binlog（drop-in 配置 `server-id=1 + log_bin + ROW`）→ `log_bin=ON`
- 建最小权限复制账号 `repl@127.0.0.1`（只授 `REPLICATION SLAVE`）
- 主库坐标 `mysql-bin.000001 @ 796` → 从库 `CHANGE MASTER` + `START SLAVE`
- **验证**：`Slave_IO_Running=Yes` + `Slave_SQL_Running=Yes` + `Seconds_Behind_Master=0`；主库建表插 3 行 → 从库自动同步 ✅

### 2. 备份恢复（含 PITR）
- `mysqldump --single-transaction` 全量备份（3 行）
- 备份后插入 2 行（耳机/U盘）→ 模拟误删这 2 行
- 恢复：全量还原（3 行）→ **binlog 位置重放 `[2137, 2404)`** → **5 行全部找回** ✅
- 教训：`--start-datetime` 与 binlog 时间戳格式不匹配（`#260805` vs ISO），**位置式 PITR 更可靠**

### 3. 故障演练（杀主库）
| 时刻 | 动作 | 结果 |
|---|---|---|
| 07:40:29 | 杀主库 `service mariadb stop` | 3306 停 |
| 07:40:30 | 从库 `STOP SLAVE; RESET SLAVE ALL` 转正 | 接管 |
| 07:40:30 | 新主写入验证 | ✅ 可写（6 行） |

**接管耗时 ~1 秒**，远低于 10 分钟验收线 ✅

### 4. 旧主重接（角色翻转）
- 旧主重启 → 作为从库挂到新主（3307）
- **踩坑**：抓新主坐标时机晚了一步 → 跳过 id 8（数据缺失）；dump 管道写错 → 静默失败；重放起点不对齐 → 重复键 1062
- **修正**：新主全量重建旧主（`mariadb-dump --master-data=1`）+ 坐标对齐
- **最终**：IO Yes / SQL Yes / 0 behind；8 行 = 8 行，持续同步 ✅

## 三、发现的问题（真实，已修正）

| # | 问题 | 后果 | 修正 |
|---|---|---|---|
| 1 | 故障切换瞬间才抓新主坐标 | 错过切换前写入 → 丢数据 | 切换瞬间记录坐标，或落后节点全量重建 |
| 2 | `--start-datetime` 格式不匹配 | PITR 重放失败 | 用 binlog 位置过滤 |
| 3 | dump 管道把密码当 SQL | 恢复静默失败 | dump 落盘 + 明确指定库 |
| 4 | 重放起点含已应用事件 | 重复键 1062 | 对齐到当前坐标或全量重建 |

## 四、结论

- **验收通过**：主从故障 10 分钟内恢复（实测 ~1 秒）
- **关键认知**：复制跑通 ≠ 恢复跑通——**备份恢复和故障演练是两码事，都真做一遍才放心**（本报告就是"真做一遍"的证据）
- **生产建议**：切换瞬间定坐标、落后节点全量重建、PITR 用位置、演练要常做
